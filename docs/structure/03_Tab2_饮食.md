## 1. 入口与整体结构

- **入口**：底部 TabBar 第 2 个位置，图标 `fork.knife`，文字「饮食」。也可以从 Dashboard 的「餐食快照」格子、Dashboard 空状态引导按钮、AI Tab 未配置提示等多个地方间接跳转过来（都会带上 `foodFocusMealType` 或 `foodScrollMealType` 语境）。
- **导航标题**：固定文字「饮食」（不像 Dashboard 会显示具体日期）。
- **整体布局**：`NavigationStack` → `ScrollViewReader`（用于程序化滚动定位）→ `ZStack(alignment: .bottom)` 叠放「可滚动内容」和「悬浮底部工具条」：

```text
1. dayControlPanel        日期选择（复用 DaySelectorView，和 Dashboard 同一个组件）
2. inlineSearchBar         内联搜索框（自绘，不是系统 .searchable）
3. summaryPanel            今日摄入摘要（进度条版，比 Dashboard 的环形进度更紧凑）
4. quickActionsPanel       快捷记录（5 个快捷入口 + 3 条横滑推荐带）
5. macroSummaryPanel       营养摘要（三大营养素 + 4 个提示格子）
6. todayDietSummaryPanel   今天饮食小结（规则文案生成的轻量点评）
7. [条件] historySearchPanel   仅搜索时出现：历史/常用食物匹配结果
8. [条件] loadingPanel / emptyState / noSearchResultPanel / mealList  四选一，取决于加载状态、当天有无记录、搜索有无结果
```

底部悬浮 `bottomBar`：`.ultraThinMaterial` 毛玻璃背景，左侧「当天合计」文字+数值，右侧黑色「添加一餐」胶囊按钮——**这是整个 Tab 最高优先级的常驻 CTA，任何滚动位置都可见**。

**生命周期钩子**：
- `.task(id: selectedDate)`：日期变化时先 `prepareDayChange()`（清空搜索框 + 160ms 的人工 loading 态，纯 UI 缓冲，不是真的在等待网络或磁盘 I/O）再 `refreshHealthTDEE()`
- `.onAppear` + `.onChange(of: appViewModel.foodScrollMealType)`：处理从 Dashboard 等页面带过来的深链接语境，见下方「2.9 跨页面深链接」

## 2. 逐面板详解

### 2.1 日期选择（`dayControlPanel`）

与 Dashboard 完全相同的 `DaySelectorView` 组件，绑定同一个 `appViewModel.selectedDate`。这是全 App 目前唯一被两个不同 Tab 直接复用的组件实例（其它共享组件是「同一个类型被多处用」，这个是「同一个类型 + 同一份数据绑定被两处用」）。

### 2.2 内联搜索框（`inlineSearchBar`）

自绘输入框（不是系统 `.searchable`）：放大镜图标 + `TextField` + 有内容时右侧出现的清空按钮（26×26 圆角方块）。搜索范围覆盖「当天食物、餐次或历史食物」（placeholder 原文）——**这一个输入框同时驱动两种完全不同的结果集**：
- 有搜索词时，`mealList` 区域从「当天全部餐次」收窄为 `filteredMeals`（只保留餐次名或食物名匹配的当天记录）
- 同时触发面板 7「历史食物」区域出现，展示**跨越所有历史日期**匹配到的常用食物和历史食物（`favoriteSearchFoods`/`historicalSearchItems`，各自最多 6 条）

也就是说这一个搜索框回答的是两个问题：「今天吃的东西里有没有匹配的」+「我以前是不是吃过/存过匹配的东西，可以直接加进今天」。

### 2.3 今日摄入（`summaryPanel`）

比 Dashboard Hero Card 更紧凑的版本：左侧「总摄入」大数字（38pt，Dashboard 是 42pt）+「/ 目标 kcal」，右侧两个纵向徽标（剩余/超出 + 「X 餐」），底部一条线性 `ProgressView`（Dashboard 用的是环形）。目标热量计算逻辑与 Dashboard 相同（`effectiveTarget`），但**这里是本 Tab 独立计算的一份 `effectiveCalorieTarget`，不是从 Dashboard 传值过来的**——两个 Tab 各自 `@Query` 同样的 `AppSettings`/`NutritionGoal` 数据、各自调用同一个 `effectiveTarget(healthTDEE:goal:)` 方法，属于「同一逻辑、独立计算两遍」，不是共享一份计算结果。

### 2.4 快捷记录（`quickActionsPanel`）—— 本 Tab 交互最密集的面板

**第一排 5 个入口**（2 列网格 + 1 个 Menu，共 5 个格子）：

| 入口 | 图标 | 行为 |
|---|---|---|
| 拍照识别 | `camera.fill` | `appViewModel.selectedTab = .ai`——**直接跳到 AI Tab**，不在本 Tab 内处理拍照，04 篇会展开 AI Tab 具体怎么识别食物 |
| 手动添加 | `plus` | `selectedMealType = dashboardFoodFocusMealType ?? guessMealType()` 后打开 `AddMealSheet` |
| 批量添加 | `checklist` | 若无可选食物（`userFoods`和`recentFoodItems`都为空），弹全局 Toast「暂无可批量添加的食物」并中止；否则打开 `BatchFoodAddSheet` |
| 模板库 | `doc.on.doc` | 若模板和饮品库都为空，弹 Toast「暂无模板」并中止；否则调用 `startTemplateImport()` |
| 复制昨天 | `clock.arrow.circlepath` | 是一个 `Menu`（非普通按钮），列出昨天每个有记录的餐次（餐次名+热量），点击调用 `copyMeal(_:)` |

**`guessMealType()` 的实现**是 `MealType.guessByTime()`（定义在 Model 层，未在本篇展开源码，逻辑是根据当前时钟推断该记哪一餐），凡是本 Tab 里「手动添加」「批量添加」「常用食物/最近吃过点击直接加」这几处入口，只要没有显式指定餐次，都统一走这个按时间推断的逻辑——是本 Tab 默认餐次归属的唯一算法来源。

**「批量添加」和「模板库」都有前置校验+ Toast 拦截**，「拍照识别」「手动添加」「复制昨天」没有——**这是三种不同的"入口前置状态处理"策略并存**：直接跳转型（拍照/手动）不做数据校验，选择器型（批量/模板）在数据为空时提前拦截并给出解释，Menu 型（复制昨天）把「昨天没有可复制的餐食」直接做成 Menu 里唯一一个不可点的选项文字，是第三种处理方式。

**第一排下方最多 3 条横滑推荐带**（各自独立条件渲染，`SystemPanelDivider` 分隔）：
1. **模板库**（`mealLibraryTemplates` 非空时）：横滑显示前 4 个使用最频繁的餐食模板，`QuickFoodChip` 展示（名称/餐次+热量），点击直接 `createMeal(from:)` 落盘，**不弹确认，点了就加**
2. **常用食物**（`userFoods` 非空时）：横滑前 6 个（按 `useCount` 降序），点击 `addUserFood(_:mealType:)`，同样直接落盘
3. **最近吃过**（`recentFoodItems` 非空时）：横滑前 8 个（跨历史日期去重后的最近食物名），点击 `addFoodItemCopy(_:mealType:)`，直接落盘

这三条推荐带的**共同特点**：点击即写入，没有二次确认或预览步骤，图标各不相同（模板橙色、常用粉色心形、最近 accent 色时钟），是三套独立的「一键复用」入口，视觉上统一用 `QuickFoodChip` 组件但底层调用的是三个不同的写入方法（全部落在 `FoodTimelineMealWriter`）。

### 2.5 营养摘要（`macroSummaryPanel`）

三个 `MacroSummaryTile`（蛋白/碳水/脂肪，各自颜色蓝/绿/橙，带独立进度条），下方 2×2 提示网格（`nutritionHint`）：
- 「目标差距」：还差 X kcal / 超出 X kcal（超出时 danger 色）
- 「这一餐可能缺」：根据蛋白/碳水/脂肪三者里目标完成率最低的一项，若最低项低于 35% 才提示具体名称，否则显示「整体尚可」——是一个简单的规则算法（`missingNutritionHint`），不调用 AI
- 「钠」「糖」：分别对比目标值，超出显示「偏高」warning 色，否则显示具体数值

### 2.6 今天饮食小结（`todayDietSummaryPanel`）

一段规则文案（`todayDietSummaryText`，纯 `if-else` 链，非 AI 生成）+ 下方 2×2 提示网格（记录完整度/食物数量/蛋白执行/能量状态）。文案规则优先级：总热量为 0 → 引导记录；超出目标 10% → 建议下一餐高蛋白低油；蛋白低于目标 50% → 建议补蛋白；钠或糖超标 → 建议减少调味/甜饮/加工食品；以上都不满足 → 「整体比较平稳」的正向反馈。**这是一套纯本地规则引擎，不消耗 AI 请求额度，任何时候（包括未配置 AI）都能显示**。

### 2.7 历史食物（`historySearchPanel`，仅搜索时出现）

已在 2.2 节说明触发条件。内容分两组：「常用匹配」（来自 `UserFood`）+「历史匹配」（来自过去所有日期的 `FoodItem`），各自最多显示对应上限条数，点击都是直接落盘添加到 `guessMealType()` 推断出的当天餐次，同样无二次确认。

### 2.8 主列表区（四选一）

- **`loadingPanel`**：日期切换后 160ms 内显示，`ProgressView` + 「正在载入当天数据」——纯视觉缓冲，不代表真的在等待异步数据
- **`emptyState`**：当天无记录且搜索框为空。用共享 `AppEmptyStateView` + 两个额外按钮（黑色「拍照记录」跳 AI Tab / 描边「手动添加」开表单）——**这是本 Tab 唯一一处空状态还带了行动按钮的地方**，其它空状态（历史搜索无结果等）只展示提示文字
- **`noSearchResultPanel`**：有搜索词但当天记录里没匹配到，纯文字提示「没有找到"XXX"」，无行动按钮
- **`mealList`**：按 `MealType.allCases` 顺序遍历，每个类型渲染一个 `MealTypeSection`（详见 2.10）

### 2.9 跨页面深链接（`applyPendingFoodFocus`）

响应 `AppViewModel` 的两个不同字段，行为不同（呼应 02 篇 Dashboard 侧「已记录」vs「可补记」两种跳转）：
- **`foodScrollMealType`**（来自「已记录」餐次的点击）：清空搜索词，切到该餐次，**用 `ScrollViewProxy` 程序化滚动**（`DispatchQueue.main.asyncAfter(deadline: .now() + 0.25)` 延迟 0.25 秒后 `withAnimation(.snappy(duration: 0.34))` 滚动到对应 `MealTypeSection` 的 `.id()`）——**先让页面渲染完成，再动画滚过去**，不是立即跳转
- **`foodFocusMealType`**（来自「可补记」的点击）：不滚动，只是把 `selectedMealType` 和 `dashboardFoodFocusMealType` 设置好——为后续用户点「手动添加」/「模板库」时预填正确的餐次做准备，这两个操作不会自动弹出添加表单，需要用户自己再点一次

`.onChange(of: appViewModel.foodScrollMealType)` 和 `.onAppear` 都调用同一个 `applyPendingFoodFocus`，覆盖「跳转时页面还没创建」和「页面已存在、二次跳转」两种时序。

### 2.10 每个餐次分组（`MealTypeSection`，定义在 `FoodTimelineComponents.swift`）

- 头部：图标+餐次名+右侧徽标（未记录=neutral「未记录」/已记录=accent「X kcal」）+ 一行「蛋白/碳水/脂肪」克数摘要 + 右侧独立的 32×32「+」按钮（**这个「+」和标题栏是分开的两个可点击区域，不是整行可点**）
- 有记录时额外显示一条 `MacroRatioBar`：三色横条（蓝/绿/橙），按蛋白×4/碳水×4/脂肪×9 的热量占比分配宽度（`max(width, 6)` 保证极小占比也有最小可视宽度），下方跟着百分比图例
- 空状态：一整行可点的虚线感提示条「记录\(类型)  +」
- 有记录：垂直堆叠该餐次下的每个 `MealCardView`（一个类型下可以有多张 `Meal` 卡片，不是每个餐次固定一张）

### 2.11 单餐卡片（`MealCardView`）—— 展示单元的核心

- **头部**（可点击折叠/展开，`isExpanded` 默认 `true`）：图标+餐次名+来源徽标（MANUAL/AI TEXT/AI PHOTO，三种数据来源）+ 若来自模板还会额外显示模板名（从 `note` 字段里用两种不同的字符串前缀规则解析出来，`templateTitle` 计算属性）+ 时间和项目数 + 右侧总热量大字 + 展开/收起箭头
- **拍照记录会显示缩略图**（`meal.photoThumbnail`），最高 160pt，点击图片直接打开 `MealDetailSheet`
- **食物明细列表**（展开时）：超过 5 项默认只显示前 5 条 + 「还有 X 项」展开按钮；点击列表区域（非按钮）同样打开 `MealDetailSheet`；每条食物行是 `FoodItemRow`，长按呼出 `contextMenu`（编辑/删除）
- **底部操作条**：左「添加食物」（打开 `AddFoodSheet`）+ 右「存到模板库」（`alert` 输入模板名后保存），中间 1pt 竖线分隔
- **长按整张卡片**呼出 `contextMenu`：「更改餐次」子菜单（`MealType.allCases` 逐个可选，当前选中项显示 checkmark）、「保存到模板库」（和底部按钮功能相同，入口重复）、「删除整餐」（`role: .destructive`，**点击立即删除，没有二次确认弹窗**）

### 2.12 整餐详情（`MealDetailSheet`）—— 只读页

顶部摘要卡（图标+餐次名+时间+总热量+蛋白碳水脂肪三格），有拍照则显示大图，下方「食物明细」区块（每条含名称/份量/热量+蛋白碳水脂肪纤维四个 micro 标签+非直接录入的营养基准提示文字），若存在任何非零营养素总量则显示「全部营养素」分组明细（复用 `NutrientDefinitions.dashboardGroups`，与 Dashboard 展开面板同源数据结构但独立布局代码），最后若有食物带 `nutritionDataNote` 则显示「配料与来源」区块。整个页面**只有一个「完成」按钮关闭**，没有任何编辑入口——编辑要回到 `MealCardView` 长按具体某条食物。

### 2.13 添加一餐（`AddMealSheet`）与添加食物（`AddFoodSheet`）

`AddMealSheet` 本身很薄：`.onAppear` 时如果传入的 `mealType`+`date` 组合还没有对应 `Meal` 记录就新建一条并立即 `insert`（**这意味着打开这个 Sheet 就已经在数据库里创建了一条空餐记录，即使用户什么都不填直接取消退出**——这也是为什么 `FoodTimelineView` 的 `AddMealSheet` 用了 `.sheet(isPresented:onDismiss: cleanupEmptyMeals)`，`onDismiss` 时调用 `FoodTimelineMealWriter.cleanupEmptyMeals` 清理掉那些「创建了但一条食物都没加」的空餐，做兜底清理）。页面内容本身只是列出已加的食物 + 「继续添加食物」按钮，实际录入营养数据在下一层 `AddFoodSheet`。

`AddFoodSheet`（单条食物的完整录入表单，本 Tab 字段最多的界面之一）：
- **食物信息**：名称输入框（`.onChange` 实时触发 `searchFood(_:)`，**只匹配 `UserFood`，不搜索历史 `FoodItem`**——与 2.2 节的搜索框行为不同，那里两种来源都搜）+ 最多 5 条匹配结果（「我的」accent 徽标 + 可能的「估算」warning 徽标，但 `isEstimate` 目前恒为 `false`，这个徽标在当前代码路径下从未真正触发过）；点结果 `applySearchResult(_:)` 一次性回填全部营养字段
- **份量**：数值+单位 Picker（g/ml/份/个/杯/碗/片/块），非 g/ml 单位时额外要求填「1单位=多少克」的换算行
- **核心营养**：热量+蛋白+碳水+脂肪，4 个 `NutritionField`（**这是文件内部私有重写的一份组件，和公开的 `NutritionEditField` 逐行相同，见「实现特点」**）
- **扩展营养**：纤维/钠/糖/胆固醇/咖啡因/茶多酚+11 种维生素矿物质，共 17 个可选字段
- **保存选项**：一个 Toggle「收藏到我的食物」，勾选后保存的同时会额外插入一条 `UserFood`（按当前克重反推出 `caloriesPer100g` 数值，只写这一个legacy 字段，不写 `servingNutrition` 字典）——**这是和设置页餐食库自己的编辑器（06 篇 `UserFoodEditorView`）不同的一条 `UserFood` 写入路径**：`UserFoodEditorView` 走的是新的"每份营养"口径（写入 `servingNutrition` JSON 字典），这里走的是旧的"每100g"口径。读取时靠 `food.servingNutrition["calories"] ?? food.caloriesPer100g` 这类 `??` 兜底两边都能显示热量，但蛋白/碳水/脂肪等其它字段不一定有类似兜底——同一个 `UserFood` 模型，因为创建入口不同，实际携带的字段结构不完全一致。
- **没有「官方标签换算」面板，也没有「来源备注」字段**——这两项只在 `EditFoodSheet` 里才有，是本篇「实现特点」里点名的 Add/Edit 不对称之一

### 2.14 编辑食物（`EditFoodSheet`）—— 字段比 Add 多两个面板

除了和 `AddFoodSheet` 相同的「食物信息/核心营养/扩展营养」外，额外多出：
- **官方标签面板**：`Picker(.segmented)` 选数据基准（直接录入/每100g/每100ml/每份）+ 三行「标签基准量/实际食用量/包装净含量」（各自数值+单位）+「按官方标签自动换算本次摄入」按钮（只有基准量和食用量都>0 时才可点，`applyOfficialLabelData()` 会把当前营养字段当作标签基准值，按比例换算成实际食用量对应的数值）
- **来源备注面板**：多行文本框，记录数据来源/配料/备注

也就是说：**新增食物时只能填「这次吃了多少」的最终数值；如果日后发现营养成分表标注的是"每100g"或"每份"而不是"整份实际吃的量"，需要先保存、再进编辑页用官方标签面板重新换算**——这是一个只在编辑路径上才存在的能力，首次添加路径没有暴露给用户。

### 2.15 从模板库创建（`TemplatePickerView`）

`.searchable` 系统搜索框（**这是本 Tab 唯一使用系统原生搜索框的地方**，2.2 节的内联搜索是自绘的，两者视觉和交互都不同），内容分两组：
- **餐食模板**：平铺列表，每行「图标+名称+餐次徽标+项目数/热量/使用次数」，点击直接创建
- **饮品库**：按品牌分组折叠（`TemplatePickerDrinkBrandGroupSection`，与饮品库管理页的分组折叠是各自独立实现的一套逻辑，非共享组件），搜索时**强制全部展开**（`!normalizedSearchText.isEmpty || expandedDrinkBrandKeys.contains(...)`），未搜索时按用户手动展开状态显示

选中餐食模板调用 `onSelect`（外部是 `createMeal(from:)`），选中饮品调用 `onSelectDrink`（外部是 `createDrinkMeal(from:)`，餐次固定用 `consumeTemplateMealTypeOverride() ?? .snack`——饮品默认记为零食/饮品类，与 01/02 篇提到的「AI 对话里饮品也归 snack」是同一套约定）。

### 2.16 批量添加（`BatchFoodAddSheet`）

两组多选列表（常用食物/最近吃过），每行是可勾选的 `BatchSelectableRow`（方形勾选框），底部确认按钮显示已选数量「添加 X」，为 0 时禁用。选中的食物统一按 `guessMealType()` 推断出的**同一个餐次**批量写入（不支持在这个界面里给不同食物分配不同餐次）。

## 3. 值得注意的实现特点

1. **`NutritionField`（`AddFoodView.swift` 内 `private struct`）和 `NutritionEditField`（独立公开文件）是同一个组件的两份实现**：字段结构、样式代码逐行相同，只是名字不同、可见性不同。`AddFoodSheet` 用前者，`EditFoodSheet` 用后者——这是本篇发现的一处具体的重复代码，理论上删掉 `AddFoodView.swift` 里的私有版本、改用公开的 `NutritionEditField` 即可消除重复，不影响任何视觉效果。
2. **Add 和 Edit 两条路径字段不对等**：编辑页比新增页多「官方标签换算」和「来源备注」两个完整面板。新增时如果想用标签换算功能，必须先随便存一个值、再进编辑页重新算。
3. **三种"数据为空时的入口保护"策略并存**（2.4 节）：直接跳转不做校验、选择器型提前拦截+Toast、Menu 型把提示做成不可点选项——同一个面板内三种策略混用。
4. **横滑推荐带（模板/常用/最近）与历史搜索结果都是"点击即落盘，无二次确认"**，与 `MealCardView` 里的「删除整餐」同样没有二次确认——**本 Tab 内所有写入和删除操作都不设置二次确认弹窗**，是一个贯穿全 Tab 的一致设计（相比 Dashboard 的饮水记录还有 3 秒撤销机制，本 Tab 连撤销都没有，只能进详情页手动删除/编辑）。
5. **`summaryPanel` 的目标热量是本 Tab 独立计算的**，不是从 Dashboard 传值，两边各自 `@Query` + 各自调用 `effectiveTarget`，理论上任意时刻两个 Tab 显示的数字应该一致（因为算法和数据源相同），但这是"两处独立实现出来结果一致"，不是"同一份计算结果被复用"。
6. **`FoodTimelineMealWriter` 是纯逻辑层**，不含任何 SwiftUI 代码，`FoodTimelineView` 的所有写入方法（`createMeal`/`createDrinkMeal`/`copyMeal`/`addFoodItemCopy`/`addUserFood`）全部只是转发调用，自己不碰 `modelContext.insert`——这是本 Tab 少数几个把「业务写入逻辑」和「界面」拆干净的例子（对比 `AddFoodSheet`/`EditFoodSheet` 的 `save()` 方法都是直接在 View 里操作 `modelContext`）。
7. **`AddMealSheet` 一打开就建空记录**，配合 `onDismiss` 兜底清理——这是一种「先乐观创建、后清理」的实现思路，而不是「先收集完数据、最后一次性创建」。

## 4. 可复制性 / 迁移建议

- **`MealTypeSection` + `MealCardView` 的两层结构（按类型分组 → 组内多张可折叠卡片）**是「有限分类、每类下可有多条记录」场景的通用模式，1Track 的订阅分类、1Day 的任务分组都可以参考这个结构，而不是简单的扁平列表。
- **`FoodTimelineMealWriter` 这种「View 只转发、纯逻辑单独成文件」的写法**值得作为家族级规范推广——本篇 3.6 条已指出这在本 Tab 内部也不是全面贯彻的（`AddFoodSheet`/`EditFoodSheet` 就没有拆），建议其它 App 新写数据写入逻辑时直接按这个模式来，1Life 自己也值得找机会把 `AddFoodSheet.save()` 这类方法收拢进对应的 Writer。
- **快捷记录面板"多条横滑推荐带＋点击即落盘"的模式**是加快高频操作的有效设计，但缺二次确认在其它 App 如果涉及金额（比如 1Cash 的快捷记账）需要重新评估是否合适——1Life 这里代价是食物记录，记错了成本低，其它领域未必如此。
- **"新增字段少、编辑字段多"这种不对称设计不建议作为家族模式照搬**，更像是 1Life 自己迭代过程中把"官方标签换算"这种高级功能后补进了编辑页却没同步补回新增页的历史遗留，建议其它 App 设计表单时让 Add/Edit 共享同一套字段面板（本身就能顺便消除本篇发现的 `NutritionField`/`NutritionEditField` 重复问题）。
